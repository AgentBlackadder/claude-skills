# Planning templates

Three scales: the day, the week, a project. Each one is built to be read by the
doer, the tempted present-moment self, so they are short on purpose.

## Daily plan (five minutes, the night before or first thing)

```
Date:
ONE THING:       <if only this gets done, the day was a win>
Done means:      <a visible finish line>
First action:    <physical, under two minutes>
Block:           <start–end time>   Place: <where>
Predicted snag:  If <obstacle>, then I will <response>.
Guard:           <friction change / blocker / co-worker / deadline>
Then (max 2):    1.            2.
Shallow window:  <one set time for email and messages, e.g. 12:30–13:00>
Shutdown:        <end time; write tomorrow's first action before stopping>
```

Checks before accepting it:

- Could the first action be done with eyes half-open? If not, make it smaller.
- Is "done means" something you'd see, such as a file, a count or a sent
  message?
- Does the block sit in the user's sharpest hours? Ask when those are.
- Is there a real gap for things that go wrong? Plan to about 70% of the day's
  capacity and leave the rest empty. That percentage is a practitioner
  heuristic, not a research finding, so tune it with the review.

## Weekly plan (twenty minutes, after `akrasia-review`)

```
Week of:
The one outcome that makes this week a win:
Why it matters (one line, from akrasia-contrast if needed):
Main inner obstacle this week:   If … then …
Days' ONE THINGs:  Mon      Tue      Wed      Thu      Fri
Protected focus blocks (time, day):
Commitment device for the week (from akrasia-commit):
The one experiment carried over from last review:
Deliberately NOT doing this week:
```

The "not doing" line matters as much as the rest. Naming what is being dropped
stops it from nagging, and nagging is a focus leak (see
[context-switching.md](../../akrasia-focus/references/context-switching.md) on
open loops).

## Project plan (backwards from the finish)

Long delay is the lever that kills projects. The fix is to bring the deadline
close by giving the project many small, dated finishes.

1. **Finish line.** What exists when this is done? Describe the object, not the
   activity.
2. **Work backwards.** List the milestones, each one reachable in a week or
   less, each with a date and a visible output.
3. **Unpack the first milestone** into tasks of a day or less. Listing the
   component steps makes time estimates more realistic (Kruger & Evans, 2004;
   see [planning-fallacy.md](../../akrasia-review/references/planning-fallacy.md)).
4. **Attach a referee** to each milestone: someone who sees the output on its
   date (`akrasia-commit`).
5. **Start today** with the first two-minute action, so the project exists
   before the planning session ends.

```
Project:
Finish line (the object):
Milestones (≤ 1 week each):  date — output — referee
First milestone, unpacked:   task — estimate — actual (fill in later)
Today's two-minute start:
```

## Anti-patterns to catch

- **Planning as procrastination.** Colour-coding, app-switching and endless
  re-planning feel like progress. If planning takes longer than the time
  suggested above, stop and do the first action.
- **Tasks without a verb** ("Tax", "Website"). These are topics, not tasks.
  Rewrite them as "Download the bank CSV for July".
- **Every task marked priority.** Then nothing is. Keep one must-win.
- **A plan that needs a perfect day.** The day will not be perfect. Plan for the
  one you'll actually have.
